# Add-only inventory import

Status: source/tests, isolated PostgreSQL repository acceptance and isolated
HTTPS acceptance completed. Migrations were applied only to synthetic databases.
Backend and Windows candidate builds completed. Operator checks on isolated
Windows HTTPS fixtures confirmed import, sign-out/sign-in persistence and unsent
draft navigation. Remaining native checks, commit and deployment stay pending.
Existing Inspect remains separate and read-only.

## Opt-in prerequisites

- Backend `ASSET_IMPORT_ENABLED` defaults to false. Only exact `true` enables
  `POST /api/v1/assets/import`; ambiguous values fail startup.
- Enabling requires separately reviewed/applied migration
  `backend/migrations/003-asset-import.sql`. Startup checks readiness without
  creating or repairing schema.
- Flutter compile-time `ASSET_DESK_ENABLE_IMPORT` defaults to false and passes
  the explicit app/page navigation opt-in. The isolated Windows candidate used it.
- Navigation requires both session and import capabilities. Ordinary inventory
  stores do not gain mutation behavior.

## Request and transaction contract

The client validates a complete inventory export v1 before preparing a request.
It submits only name, category, serial, status and notes. Source IDs, owner,
timestamps, versions and client digests are forbidden. Duplicate labels/serials
remain separate assets. Limits: 1-500 records and 1 MiB serialized UTF-8.

The server validates the complete batch before acquiring a connection, rejects
malformed Unicode and normalizes field edges. It computes SHA-256 over versioned
canonical records, independent of property order and request ID. Authentication
supplies ownership, CSRF is required, query overrides are rejected and responses
use `Cache-Control: no-store`. The route-specific parser bounds raw bytes and
rejects compressed bodies; other routes retain their original limits.

One connection/READ COMMITTED transaction claims the owner/request UUID in
`assets.import_receipts` and inserts server-generated asset UUIDs in one bulk
statement. Identical replay returns original IDs; changed content conflicts.
The isolated PostgreSQL fixture verified that the unique claim serializes
concurrent same-key requests. Mock query tests alone do not prove these semantics.

Errors are sanitized and no automatic retry occurs. An ambiguous COMMIT response
or failed rollback discards the connection. Feature rollback means disabling the
route while retaining assets and receipts; dropping receipts loses replay safety.

## Client review and uncertain outcomes

The draft is deeply immutable, account-bound and retains an exact serialized
request with a UUID v4 generated by Dart `Random.secure()`. Confirmation also
binds the reviewed session revision. Receipt validation requires the exact key,
count and unique UUID v4 IDs; malformed receipts are uncertain, not success.

The separate Import page displays account, editable fields, count and operation
key. Selecting a file never writes. A checkbox plus explicit confirmation is
required. Concurrent confirmations are blocked. Unknown outcomes retain the same
draft for explicit replay and block replacing the file or leaving via Back.
Unsent drafts permit Keep/Discard confirmation; busy writes block Back.

Session events and replaced session/source/file capabilities invalidate review;
late results cannot restore it. The app removes the private navigator on sign-out.
The earlier accepted import candidate retained recovery only in memory. The new
[source/test recovery candidate](inventory-import-recovery-proposal.md) requires an
explicit private file before submission and restores the exact request for manual
replay. Native and real process-loss recovery acceptance remain pending; do not
start a new key blindly after an uncertain outcome.

## Isolated PostgreSQL acceptance

`asset-import.postgres.spec.ts` defines seven opt-in scenarios: 500-record exact
replay, changed-content conflict, two-owner isolation, identical concurrency and
conflicting concurrency, injected row failure/rollback and lost COMMIT
acknowledgment/replay. Default invocation skipped all seven without creating a
pool. Strict typecheck passed. A separately approved live run subsequently passed
all seven scenarios on PostgreSQL 17.11 using an existing immutable image.

The fixture harness must create a dedicated loopback database named
`asset_import_fixture_<12 lowercase hex>`, apply migrations 001/002/003, and create
`public.asset_import_fixture_identity` with exactly one 32-hex marker. It must
supply `ASSET_IMPORT_FIXTURE_URL`, matching `ASSET_IMPORT_FIXTURE_MARKER`, and exact
`ASSET_IMPORT_FIXTURE_OPT_IN=isolated-repository-v1`. The suite checks database
identity and marker before inserting synthetic accounts; it never migrates,
truncates or deletes. Connections and statements have five-second timeouts.
The successful run verified both fault injections against the real synthetic
database: full rollback after a row error, and exact replay after COMMIT
succeeded but its acknowledgment was deliberately lost. The container passed
ownership checks and was stopped; its volume was retained. No regular database
was involved. This is repository acceptance, not HTTP or native acceptance.

An earlier run stopped before scenarios because readiness observed the temporary
initialization server. The corrected harness requires a TCP connection and an
exact database-name query within bounded deadlines. Five offline readiness tests
passed before the separately approved new run. Further runs require new approval.

The expanded draft/operation group passed 12 tests and analyzer. Additional
regressions prove empty exports cannot become import batches, duplicate returned
IDs are rejected case-insensitively, and malformed surrogate text is rejected by
the existing strict snapshot parser before draft construction. The initial test
expected rejection later in preparation; inspection proved the earlier guard
already existed, so no duplicate production Unicode validator was retained.

Nine page tests now include late picker completion after source replacement
(no hashing or draft restoration) and explicit UI replay after uncertainty.
Replay requires a new acknowledgment and submits the identical draft instance;
file replacement stays disabled after the first attempt. Analyzer passed.
The latest PostgreSQL run passed seven tests with no skips or failures. The Jest
process finished within its 120-second deadline; no retry was performed.

## Isolated HTTPS acceptance

The reviewed backend candidate and real Dart API client passed a separate HTTPS
fixture using default certificate validation and synthetic accounts/data only.
Verified: explicit import, exact same-key replay without duplicates,
changed-content conflict, independent owner scopes, client account binding and
sign-out invalidation. A separate negative-client account verified 401 without
authentication, 403 without CSRF, invalid batches/malformed JSON rejection, and
proxy-side 413 for bodies over 1 MiB. Aggregate asset/receipt counts did not change
during negative cases; counts are not a general row-content integrity proof.

The successful run followed two separately approved failed runs. The second
identified the proxy oversize case. An offline red/green regression reproduced
premature request destruction; the repaired test proxy returned 413 successfully
in the subsequent approved run. No automatic retries were performed.
Owned processes/container stopped and the synthetic volume was retained.
This does not certify Windows native interaction or recovery after process loss.
See [the HTTPS plan](inventory-import-https-plan.md) for source and scope.
